# 01 中断异常事件分类

[本讲目录](../index.md) · [课程目录](../../index.md) · [下一节：02 中断响应与中断向量](02-interrupt-response-and-vector-table.md)

> [!abstract] 本节要点
> - **中断**来自 CPU 之外的 I/O 设备、时钟、硬件故障等，与当前指令无关，是**异步**的；**异常**由正在执行的指令引发，是**同步**的，必须立即处理。
> - 异常分三类：**陷入**（trap）是有意安排的（如系统调用），返回下一条指令；**故障**（fault）可恢复（如缺页），返回当前指令重新执行；**终止**（abort）不可恢复，不返回。
> - 中断总是返回到被打断程序的下一条指令。
> - 中断/异常机制靠软硬件配合：硬件负责**响应**（捕获请求、记录、把控制权交给处理程序），软件负责**处理**（识别类型、完成处理）。硬件做完再交给软件，两者的步骤不能交叉。
> - 请求必须先记录在中断寄存器里；同类请求在处理前再次到来可能会丢失。

## 事件分类：中断与异常

上一讲已经介绍了中断和异常的概念、引入原因，以及事件的初步划分（见 L02「08 中断与异常概念」）。本讲把这张分类表补全：每类事件从哪里来，是否与当前指令同步，处理完后回到哪里。统一术语是为了讨论问题时大家说的是同一件事。[^s4b1]

系统运行中发生的各种需要 CPU 暂停当前工作去应对的情况，笼统称为**事件**。按产生原因可分为两大类：[^s2p21]

- **中断**（Interrupt，又称外中断）：来自 CPU 之外的部件，如 I/O 中断（网卡、硬盘、键盘、鼠标、打印机）、时钟中断，以及硬件故障（如即将掉电）。
- **异常**（Exception，又称内中断、例外）：在 CPU 执行某条指令的过程中由这条指令本身引发，如系统调用、页错误/页故障、保护性异常、断点指令，以及算术溢出等其他程序性异常。

可以用课堂作类比：CPU 是正在讲课的老师。有人举手、门口来人、手机响，都是讲课之外的事，相当于中断；异常则是 CPU 执行当前这条指令的过程中，由这条指令本身引发的内部事件。判断一个事件属于哪一类，只需问一句：它是不是由当前执行的这条指令引起的？[^s4b1]

![中断与异常的事件分类](../assets/l03-interrupt-exception-events.png)

图：事件按来源分为中断与异常；表格从同步/异步、有意/意外两个维度区分 interrupt、fault、syscall trap，并给出每类事件处理完后的返回位置。

分类图给出了事件的层次：事件分为中断（I/O 中断、时钟中断、硬件故障）和异常（系统调用、页故障、保护性异常、断点指令、其他程序性异常）；下方的表按“原因、同步/异步、返回行为”比较中断与三类异常；右上角的小表则从“是否预期”的角度给出另一种划分。

## 同步、异步与返回行为

分类之所以重要，是因为它决定了两件事：事件能不能等一等再处理，以及处理完以后回到哪里继续执行。

| 类别 | 原因 | 同步/异步 | 返回行为 |
| --- | --- | --- | --- |
| 中断（Interrupt） | 来自 I/O 设备、其他硬件部件 | 异步 | 总是返回到下一条指令 |
| 陷入（Trap） | 有意识安排的 | 同步 | 返回到下一条指令 |
| 故障（Fault） | 可恢复的错误 | 同步 | 返回到当前指令 |
| 终止（Abort） | 不可恢复的错误 | 同步 | 不会返回 |

[^s2p21]

**异步**（asynchronous）事件与当前指令无关，到达时刻不可预测，因此可以稍后处理；**同步**（synchronous）事件正是当前指令造成的，这条指令不处理完就无法继续，因此必须立刻处理。一个生活类比是：微信消息是异步的，可以过一会儿再看；电话打来时必须马上决定接不接，不接对方就无法与你通话，这像同步。[^s4b1]

三类异常的区别集中体现在返回行为上：

1. **陷入**（trap）是程序有意安排的，最典型的是系统调用。请求的服务完成后，这条陷入指令的任务就完成了，所以返回到**下一条指令**。
2. **故障**（fault）是出了错、但能修复的情况，最典型的是缺页（page fault）。操作系统把缺的页调入内存后，引发故障的那条指令还没有真正完成，所以要返回到**当前指令**重新执行。
3. **终止**（abort）是不可恢复的错误，处理程序不会返回到原程序。

中断则总是返回到下一条指令：CPU 是在一条指令执行完之后才去响应中断的，被打断的那条指令已经完成。下一章会讲到，CPU 在指令周期末尾才检查中断（见 [中断周期](02-interrupt-response-and-vector-table.md)）。

> [!example] 例：判断事件类别与返回位置
> 1. 用户按下键盘：来自 CPU 外部的 I/O 设备，属于中断，异步，处理完返回到下一条指令。
> 2. 程序执行 `int 0x80` 请求 `write`：当前指令有意引发，属于陷入，同步，返回到 `int 0x80` 之后的那条指令。
> 3. 程序访问一个尚未调入内存的页：当前指令引发、可修复，属于故障，同步，调页完成后重新执行这条访存指令。
> 4. 打印机发出“打印结束”信号：来自外部设备，属于中断。

### 与 ICS 及其他教材的术语对照

ICS（计算机系统导论）把这些事件统称为“异常”（exception），在异常之下再分出中断、陷入、故障、终止四类，其中中断来自 I/O 设备等硬件。本课先分“中断/异常”两大类，再把异常细分为三类。两种叫法只是总称不同，划分方式一致，互不矛盾。[^s4b1]

另一种角度是按“是否预期”划分：[^s2p21]

| | Unexpected（非预期） | Deliberate（有意安排） |
| --- | --- | --- |
| Exceptions（sync） | fault | syscall trap |
| Interrupts（async） | interrupt | software interrupt |

系统调用、主动发出的软件中断是程序有意安排的；缺页、外设中断则不在程序的预期之内。同一组概念从同步/异步、是否预期等不同角度去看，在不同课程里遇到时就能对上号。

## 中断/异常机制的软硬件分工

中断/异常机制是现代计算机系统的核心机制之一，要靠硬件和软件相互配合才能发挥作用。[^s2p22] 很多同学学完组成原理和 ICS 仍分不清哪些步骤由谁完成，考试时总有人把软硬件步骤交叉着写。这里先确立总原则：**硬件先做，做完转给软件，剩下的由软件做**。[^s4b1]

- **硬件做什么——中断/异常响应**：捕获中断源发出的中断/异常请求，以一定方式响应，把处理器控制权交给特定的处理程序。[^s2p22] 响应相当于决定“这件事管不管”：电话来了接不接，微信来了看不看。
- **软件做什么——中断/异常处理程序**：识别中断/异常的类型，并完成相应的处理。[^s2p22]

两部分的具体步骤分别在 [中断响应与中断向量](02-interrupt-response-and-vector-table.md) 和 [中断处理完整流程](03-hardware-software-handoff-in-interrupt-handling.md) 展开。

```mermaid
flowchart LR
  E["中断源发出请求"] --> R["中断寄存器置位（记录）"]
  R --> H["硬件：中断/异常响应"]
  H --> S["软件：中断/异常处理程序"]
  S --> B["返回被打断的程序"]
```

### 请求必须被记录

硬件捕获请求的方式是设置一个**中断寄存器**：磁盘、网卡等设备发来中断时，经电路把寄存器中对应的位置为 1，表示来了一个事件。不记录，请求就丢了。

这一点可以与 ICS 学过的**信号**（signal）对照：内核用一个位向量记录发给进程的各种信号，信号**不排队**，同一类信号在前一个还没处理时又来一个，后来的就丢了。中断寄存器按位记录请求，同样只能表示“有没有”，表示不了“来了几次”，因此同类请求在处理之前再次到来时可能丢失。[^s4b1]

### 软件处理：兵来将挡

软件处理部分的逻辑并不复杂：什么样的事件，就做什么样的处理。以打印机中断为例，同样是打印机发来的中断信号，原因可能是：

- 打印正常结束；
- 缺纸；
- 缺墨（墨粉用完）；
- 卡纸。

原因不同，处理办法就不同，例如缺纸时显示提示，让用户加纸。每一种中断都要有人写这样一段处理代码，但具体怎么处理各自清楚，本课不再细讲，重点放在软硬件如何交接。[^s4b1]

> [!warning] 易错点
> 整个过程中“硬件做的部分”和“软件做的部分”有时被口头称为“上半段”和“下半段”。这与 Linux 中断处理程序的**上半部/下半部**（top half / bottom half）不是一回事：后者是把**软件**处理程序再拆成关中断的紧急部分和开中断的非紧急部分，见 [中断处理完整流程](03-hardware-software-handoff-in-interrupt-handling.md) 中的思考题。

> [!question]- 自测：执行除法指令时除数为 0，与键盘按键，各属于哪一类？处理完分别返回哪里？
> 除零由当前指令引发，是异常（同步），属于程序性异常；按键来自外部设备，是中断（异步），返回下一条指令。除零是程序错误，操作系统无法像缺页那样把缺的东西补上，重新执行同一条指令也不会得到正确结果。

> [!question]- 自测：为什么缺页处理完要“返回当前指令”，而系统调用处理完要“返回下一条指令”？
> 缺页是故障：引发它的访存指令没有完成，调页修复后必须重新执行这条指令。系统调用是陷入：陷入指令的任务就是请求服务，服务完成即这条指令完成，所以继续执行下一条。

> [!question]- 自测：设备在同一中断请求尚未被处理时又发了一次同样的请求，会发生什么？
> 可能丢失。中断寄存器按位记录请求，位已经是 1，再置位不会多记一次，与信号用位向量记录、不排队的道理相同。
