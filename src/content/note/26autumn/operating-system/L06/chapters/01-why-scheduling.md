# 01 为什么需要调度

[本讲目录](../index.md) · [课程目录](../../index.md) · [下一节：02 调度层次与处理器调度](02-scheduling-levels-and-processor-scheduling.md)

> [!abstract] 本节要点
> - 操作系统为进程运行服务；每次中断、异常、系统调用处理完、返回用户态之前都要经过调度，由调度决定谁上 CPU、上多久。
> - 进程调度的根本问题：多个进程竞争**有限的、可被抢占的** CPU；要回答怎么分配、何时切换、切换代价多大。
> - 大模型推理引擎（如 vLLM）也在做调度：对象是用户请求和 token 生成任务，资源是 GPU、显存和 KV cache，目标同样是高吞吐、低延迟、公平、不饥饿。
> - 资源池化把多种（可能跨节点的）物理资源抽象成统一调配、共享使用的逻辑资源，是调度的前置条件；层次从单机、虚拟机、集群（K8S）到 GPU 池化。
> - 单 CPU 只能**并发**，多处理器才可能**并行**；调度问题按 When、How、What 展开，不存在适合所有系统的调度算法。

## 调度在操作系统中的位置

前几讲的内容都指向同一件事：操作系统是为进程运行服务的。没有进程运行，操作系统什么也不用做。服务过程中，进程有时暂时得不到资源，有时占用资源太久，有时出错，有时收到别的进程或设备发来的信号（软信号、硬件中断），这些情况都由底层的中断/异常机制统一处理（见 L03「03 中断处理完整流程」），进程在各状态之间的转移由进程模型描述（见 L04「03 三状态模型」、L04「04 扩展状态与实际系统」和 L05「01 进程表与队列模型」）。

这些机制最后都落到**进程调度**上：谁上 CPU、上多长时间，都由调度模块决定。前面讲过，中断或异常进入内核后，不管是哪类事件，内核处理完都要走到出口，而出口处一定经过调度。调度可以不重新选人，也可以重新选人，控制权交给调度来决策，所以这部分内容很重要。[^s3b1] 出口处“要不要重新选人”由 `need_resched` 一类标志判断，见[进程切换与上下文切换](04-process-switch-and-context-switch.md)。

**进程调度的根本问题**：多个进程竞争**有限的、可被抢占的** CPU 资源。[^s3b1] 由此产生三个具体问题：

1. **如何分配 CPU**：按什么原则把 CPU 给谁。
2. **何时切换**：在什么时刻做出“换人”的决定。
3. **切换代价多大**：换人本身要花时间和空间。

切换有代价，可以拿 4×100 米接力来比：选手跑本身没问题，最花时间的是交接棒。交接要准确，又不能为了稳妥把速度降得太低；交接做不好、掉了棒，损失更大。进程切换也一样，既要把旧进程妥善安置好，又不能太慢、太频繁。

## 今天的调度场景：大模型推理与资源池化

调度不只发生在进程之间。大模型服务（如 DeepSeek、ChatGPT）提供的是算力：用户发来推理请求，系统要决定怎样调配算力来为这些请求服务，这同样是一整套调度策略，只是在不同的层面上。[^s3b1]

以推理引擎 vLLM 为例，它的调度器和操作系统的进程调度器几乎一一对应：

| 对比项 | 操作系统进程调度 | 大模型推理调度（如 vLLM） |
| --- | --- | --- |
| 调度对象 | 进程或线程 | 用户请求、token 生成任务 |
| 被分配的资源 | CPU（多个核） | GPU、显存、KV cache |
| 排队结构 | 就绪队列 | 等待处理的请求队列 |
| 调度决策 | 谁上 CPU 运行（running） | 谁在 GPU 上执行 |
| 资源不足时 | 抢占正在运行的进程 | 显存不足时抢占部分请求，或按优先级抢占 |
| 内存管理 | 虚拟存储 | 用 PagedAttention 管理 KV cache，思路类似虚存 |
| 目标 | 高吞吐、低延迟、公平、不饥饿 | 同样是高吞吐、低延迟、公平、不饥饿 |

时间片的概念在推理场景中也有对应：进程“上 CPU 运行多长时间”，变成了对 KV cache 块这类资源的分配。表中最后一行的目标在后面会反复出现，尤其是**不饥饿**：某些请求或进程长期得不到资源时该怎么办。低延迟在具身智能、自动驾驶等场景中是硬性要求，延迟过长，车辆就来不及反应。[^s3b1]

> [!note] 补充解释
> PagedAttention 是 vLLM 提出的 KV cache 管理方法：把每个请求的 KV cache 切成固定大小的块，块在显存中不必连续，用一张块表记录“逻辑块→物理块”的映射，按需分配，用完回收。这和虚拟存储中“页→页框”的映射与按需分配是同一种思路。细节可参考 vLLM 论文 [Efficient Memory Management for Large Language Model Serving with PagedAttention](https://arxiv.org/abs/2309.06180)。

**资源池化**（resource pooling）是另一个与调度紧密相关的概念：把多种、可能跨节点的物理资源整合起来，抽象成一个逻辑资源，使其可以被统一调配、共享使用。[^s3b1] 单机时资源很简单；跨节点后 CPU、内存、加速卡分散在很多机器上，必须先整合，再统一调度。

资源池化是调度的**前置条件**：先做池化，再在其上做调度，池化为调度提供了“舞台”，决定调度器能看到哪些资源、以多粗或多细的粒度看到。池化的层次如下：[^s3b1]

| 池化层次 | 资源形态 | 调度在做什么 |
| --- | --- | --- |
| 无池化（单机） | 一个 CPU、一块内存 | 进程、线程在这台机器上轮流运行 |
| 虚拟机 | 虚拟化后可有多个 CPU | 按时间片分配 CPU |
| 集群（如 K8S） | 一堆节点的资源统一管理，以容器等形式使用 | 在统一的节点资源上分配 |
| 大模型 GPU 池化 | 很多卡汇成的算力 | 把多卡算力分配给推理请求 |

统一管理的目的有三：提高资源利用率；更灵活、可扩展，资源不够时可以扩容；统一管理降低了管理成本。[^s3b2] 所以本讲讨论的 CPU 调度虽然是最简单的情形，它的思路在这些新场景中都可以借鉴。

## 并发与并行

只有一个 CPU 时，怎么“同时”跑多个程序？靠调度让这些进程**轮流**上 CPU。看上去它们在同时执行，准确的说法是**并发**执行。[^s2p2]

- **并发**（concurrency）：在一段时间范围内，多个进程都已经开始运行、但都尚未结束。单个 CPU 只能做到并发。
- **并行**（parallelism）：多个进程在同一时刻真正同时执行，需要多个处理器。

可以用跑步来比：1500 米或马拉松，选手挤在同一条跑道上，谁跑在前面会变，像并发；跨栏比赛各跑各的道，同时推进，像并行。一个人做事也只能并发：同一时刻只能干一件，在几件事之间来回切换。ICS 课中接触的基本都是并发；有了多个处理器，才需要考虑并行计算。[^s3b2]

> [!warning] 易错点
> “同时执行”在单 CPU 上是带引号的：任一时刻 CPU 上只有一个进程在运行，其余进程处于就绪或阻塞状态。判断是并发还是并行，看的是**同一时刻**有没有多个进程真正在不同处理器上执行，而不是用户感觉它们是否同时在推进。

## 调度问题的提纲

理解一个问题可以从 5W1H（What、When、How、Which、Why 等）多个角度入手。调度主题要回答的问题可以按 When、How、What 归类：[^s2p2][^s2p3]

**When：何时调度，理由是什么。** “什么时候做”和“做的理由”其实是同一件事：没有事件发生就不需要调度，事件发生、内核处理完之后，才决定要不要重新选人。[^s3b2] 这一点在[调度时机](03-scheduling-timing.md)中详细列出。

还有一个设计系统时必须面对的细节：就绪队列可能是空的。CPU 像心脏一样，只要开机就一个周期接一个周期地运转，不能“停跳”。所以操作系统会安排一个专门的进程在没人可选时占住 CPU、不做实际工作，有事来了就立刻让出。这就是 idle 进程，见[调度层次与处理器调度](02-scheduling-levels-and-processor-scheduling.md)。

**How：如何调度。** 选出新进程后，要把原来的进程妥善安置好，让它以后能继续执行，再把新进程送上 CPU。这件事的核心是**上下文切换**（context switch），在任何操作系统代码里找到 `switch` 相关的那一段，就是真正“换人”的地方。切换有成本：太频繁不合适，太久不切换又对其他用户进程不友好，这是一个折中权衡问题。[^s3b2] 具体过程和开销见[进程切换与上下文切换](04-process-switch-and-context-switch.md)。

**What：用什么调度算法。** When 和 How 都比较确定，篇幅最多的是调度算法。如果有一个算法能“包打天下”，全世界计算机用它就行，不必讨论；但应用场景各不相同，这样的算法不存在。[^s3b2] 关于算法要关注几点：

- **不同类型的操作系统不能用同一种算法。** 实时系统、服务器/云、桌面、手机的调度算法不应相同，因为它们的目标不同。
- **目标不是越快越好。** 只求快，闭着眼随便挑一个最快，但这样会在其他方面出问题。
- **选进程要考虑多种因素。** 就像计划假期出游要同时考虑时间、经费、目的地，调度算法也不能只看单一因素。

调度算法不需要死记，但要能像工作中向主管提交方案那样，说清它的优点、缺点和适用场景。What 这一大类完整地包括：批处理、交互式、实时系统各自适用的算法，抢占式与非抢占式调度，算法的比较维度，机制与策略分离原则在调度中的应用，以及实例操作系统（Windows、Linux）的调度。[^s2p3][^s2p4] 本讲讲到设计调度算法前要考虑的目标、指标和共性问题，见[调度目标与衡量指标](05-scheduling-goals-and-metrics.md)和[调度算法设计要点](06-scheduling-design-issues.md)；具体调度算法留到后续课程。

> [!question]- 自测：一台单核笔记本上，同时开着音乐播放器和正在编译的 IDE，两者是并发还是并行？换成 8 核机器呢？
> 单核时是并发：任一时刻只有一个进程在 CPU 上，调度让它们轮流运行。8 核时，两个进程可能被分到不同的核上同一时刻执行，这时才是并行（是否真的并行取决于调度把它们放在哪些核上）。

> [!question]- 自测：在 vLLM 类推理引擎中，“显存不足时暂停一部分请求、优先服务高优先级请求”对应进程调度中的哪个概念？
> 对应**抢占**：资源不够时，强行收回正在使用资源的一部分任务的资源，交给更重要的任务。它和进程调度中“更高优先级进程就绪时剥夺当前进程的 CPU”是同一种思路。
