# 03 调度时机

[本讲目录](../index.md) · [课程目录](../../index.md) · [上一节：02 调度层次与处理器调度](02-scheduling-levels-and-processor-scheduling.md) · [下一节：04 进程切换与上下文切换](04-process-switch-and-context-switch.md)

> [!abstract] 本节要点
> - 从进程模型看有 7 种调度时机：退出、出错终止、创建新进程、运行进程阻塞、阻塞进程被唤醒、时间片用完、主动放弃 CPU。
> - 从事件看，它们一一对应于 exit/abort 异常、fork、等待 I/O、I/O 中断与唤醒、时钟中断、yield 等确定的事件。
> - 时钟中断 ≠ 时间片：时钟按固定频率发中断；时间片计时器是内存中的整数，每次时钟中断减 1，减到 0 才是“时间片到”。
> - 完整顺序：事件发生→当前进程暂停→硬件响应→进入 OS 处理事件→进程状态变化或出现新进程→就绪队列调整→按调度算法选进程；先硬件后软件，不会软硬交错。
> - 调度时机统一为**内核对中断/异常/系统调用处理后返回到用户态前的最后时刻**。

> [!tip] 课堂强调
> 调度时机的两页是核心关键，“什么时候都会考”；调度时机显而易见，要求当堂就记住。答题时尤其要注意**顺序**：以往考试总有同学把硬件和软件的步骤交错着写。[^s3b4][^s3b5]

## 从进程模型看调度时机

调度时机就是“什么时候要决定选人”。CPU 什么时候需要（或可能需要）重新选人，可以直接从进程状态模型推出来，共 7 种情况：[^s2p9]

1. **进程执行完毕并退出**：CPU 空了，必须选人。
2. **进程由于某种错误或异常而终止**：与第 1 条一样都是终止，只是一个正常、一个出错。
3. **新进程的创建**：例如父进程创建了子进程，可能需要重新调度。
4. **运行进程要等待 I/O 操作或其他资源时进入阻塞态**：Running→Blocked，CPU 空了，必须选人。
5. **被唤醒的阻塞进程重新回到就绪态**：Blocked→Ready。
6. **进程用完所分配到的时间片回到就绪队列**：Running→Ready，要重新选。
7. **进程主动放弃 CPU**：例如线程库中的 `yield` 函数，调用者主动下 CPU。

其中第 1、2、4 条是当前进程不能再运行了，CPU 空出来，显然要选人。第 5 条乍看不需要调度：CPU 上的进程还在运行，为什么一个进程从阻塞回到就绪也要重新选？原因是**就绪队列的“格局”变了**。回来的这个进程可能比正在运行的进程优先级更高，就像一个领域里本来几个强者稳坐前列，突然杀出一匹黑马，排名就要重新考虑。[^s3b4] 例如某个高优先级进程原先在等磁盘读，磁盘中断表示 `read` 完成，把它唤醒回到就绪，它就比正在运行的进程优先级高，这时可以重新调度。[^s3b9] 第 3 条同理：新创建的子进程若被赋予更高的优先级，格局也变了。

## 从事件看调度时机

同样的时机也可以从**事件**的角度描述，典型事件有：[^s2p9]

- 创建、唤醒、退出等进程控制操作；
- 进程等待 I/O、I/O 中断；
- 时钟中断，如时间片用完、计时器到时；
- 进程执行过程中出现 abort 异常；
- 执行 `yield`。

两种视角是一一对应的，只是一边看状态转换，一边看引发转换的事件。系统中定义的事件都是**确定**的：中断/异常机制定义了若干种事件，不应该出现系统不知道的事件。把中断和异常统一看作事件后，对应关系如下：[^s3b4]

| 进程模型中的时机 | 对应的事件 | 为什么要调度 |
| --- | --- | --- |
| 执行完毕退出 | 调用 `exit`（陷入内核的异常） | CPU 空出 |
| 出错或异常终止 | abort 异常 | CPU 空出 |
| 创建新进程 | `fork` 等创建操作 | 就绪队列多了新进程 |
| 等待 I/O 或资源而阻塞 | 进程发起 I/O 等待（blocked） | CPU 空出 |
| 阻塞进程被唤醒 | I/O 中断、`wakeup`/signal | 就绪队列格局变化 |
| 时间片用完 | 时钟中断 | 当前进程须让出 CPU |
| 主动放弃 CPU | 执行 `yield` | CPU 空出 |

## 时钟中断与时间片计时器

时间片用完对应的事件是时钟中断，但**时钟中断和时间片不是一回事**。[^s3b4]

- **时钟中断**来自硬件：系统中有一个定时装置，核心是晶体振荡器（石英晶体，和石英手表计时的原理相同；对精度要求极高的场合还有原子钟），它按**固定频率**向 CPU 发出中断信号。
- **时间片计时器**是软件维护的计数：本质上是一个整数。系统里这样的计时器很多（每个进程的时间片、各种定时器），寄存器放不下，所以只能放在**内存**中。[^s3b5]

二者的关系是：每次时钟中断到来，中断处理程序把这些计数减 1（一般每次减 1），某个计数减到 0，就表示这个时间片到了，或者这个定时器到时了，随后进行唤醒或重新调度。也就是说，**时钟中断这一事件导致了“时间片到”或“定时到”**，它们是调度时机的具体触发动作。[^s3b5]

> [!example] 例：时钟中断与时间片
> 设时钟每隔 $1\,{\rm ms}$ 发一次中断，进程 P 上 CPU 时时间片计数被设为 $10$。
>
> 1. 每次时钟中断，内核把 P 的计数减 1：$10 \to 9 \to \cdots \to 1$，这 9 次中断都不是“时间片到”，P 继续运行。
> 2. 第 10 次时钟中断把计数减为 $0$，内核判定 P 的时间片用完，P 回到就绪队列。
> 3. 中断处理结束、返回用户态之前进行调度，选出下一个进程。
>
> 因此时钟中断发生了 10 次，“时间片到”只发生 1 次，P 最多连续运行约 $10\,{\rm ms}$。

## 调度时机的完整链条

把上面的时机和事件串起来，一次调度时机是这样形成的：[^s2p10]

1. **事件发生**：中断、异常或系统调用。
2. **当前运行的进程暂停运行。**
3. **硬件机制响应**：不论是进程主动进入内核还是响应中断进入，硬件完成响应（见 L03「03 中断处理完整流程」）。
4. **进入操作系统，处理相应的事件**：执行对应的中断/异常处理程序或系统调用服务例程。
5. **结束处理后**：进程模型中对应的操作完成，某些进程的状态会发生变化，也可能出现新的进程。
6. **就绪队列有调整**（也可能 CPU 空出）。
7. **需要进程调度**：根据预设的调度算法，从就绪队列中选一个进程。

```mermaid
flowchart LR
    A[事件发生] --> B[当前进程暂停]
    B --> C[硬件响应]
    C --> D["进入 OS 处理事件"]
    D --> E["进程状态变化/出现新进程"]
    E --> F[就绪队列调整]
    F --> G[按调度算法选进程]
    G --> H[返回用户态]
```

这条链的**顺序**是：第 3 步之前是硬件做的，第 4 步起全部是软件（内核）做的。硬件做完交给软件，软件处理完后返回用户态继续运行，中间**不会再回到硬件**，不存在“软硬交错”。[^s3b5]

由此得到调度时机的精确表述：**内核对中断/异常/系统调用处理后，返回到用户态前的最后时刻**。[^s2p10] 不管进来时发生的是什么事件，处理完后都统一走到这个点进行调度。这体现了**机制与策略分离**：中断/异常机制统一负责“事件进来、处理、返回”，不同事件的处理是不同的策略，调度则安排在这个统一的出口上。[^s3b5] L03「07 Linux 系统调用执行」中，系统调用返回前检查 `need_resched` 标志的那段代码，就是这个“最后时刻”的具体实现。

> [!tip] 课堂强调
> 调度时机、中断/异常机制这部分是整个操作系统“转起来”的核心，按 80/20 原则，前面这些内容再加上虚拟存储，就是那最重要的 20%。[^s3b5]

> [!warning] 易错点
> - 把“调度程序选进程”写在“硬件响应”之前，或者在内核处理中间又插入一个硬件步骤，都是顺序错误。正确答案中硬件步骤只出现在进入内核之前。
> - 调度时机到了不等于一定换人。到达“最后时刻”时，调度可能发现无须换人，原进程继续运行；是否换人见[进程切换与上下文切换](04-process-switch-and-context-switch.md)。

> [!question]- 自测：进程 A 正在用户态运行，磁盘中断到来，唤醒了一个优先级比 A 低的进程 B。这里有没有调度时机？A 会被换下吗？
> 有调度时机：内核处理完磁盘中断、返回用户态前的最后时刻就是调度时机。但 B 优先级比 A 低，在基于优先级的调度下就绪队列的变化不足以让 A 下 CPU，调度决定不换人，A 继续运行。

> [!question]- 自测：把下列步骤排成正确顺序：①按调度算法选进程 ②硬件响应中断 ③就绪队列调整 ④时钟中断发生 ⑤内核执行时钟中断处理程序、时间片计数减到 0 ⑥当前进程暂停
> ④→⑥→②→⑤→③→①。时钟中断（事件）发生，当前进程暂停，硬件响应后进入内核处理；处理中发现时间片用完，进程回到就绪队列，队列调整后在返回用户态前按算法选进程。
